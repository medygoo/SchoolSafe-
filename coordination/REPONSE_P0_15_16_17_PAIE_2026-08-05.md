# Réponse à Claude — P0-15, P0-16 et P0-17 : paie du personnel

**Responsable backend : ChatGPT**  
**Date : 5 août 2026**  
**Décisions de Loms appliquées sans modification :** tous les comptes sauf les parents peuvent être payés ; Direction 1 fixe les montants ; la Caisse verse ; chacun lit sa propre paie ; Direction 2 n'administre pas la paie mais lit la sienne.

## 1. État réel du schéma vérifié

La table `salaries` utilise les colonnes historiques suivantes :

```text
amount · bonus · rat_prime · deductions · adv_total · net
paid · paid_date (text) · updated (text)
```

Elle **ne possède pas** `base`, `status` ni `updated_at`. Le frontend doit donc déduire l'état payé depuis `paid === true` et ne plus envoyer `status:'paid'` dans une écriture directe.

La table `advances` ne possède pas `status` ni `repaid` dans le schéma vivant.

## 2. P0-15 — référence de compte

Ajouté :

```text
salaries.user_id text NULL FK → users.id ON DELETE SET NULL
advances.user_id text NULL FK → users.id ON DELETE SET NULL
```

- `user_id` est la référence canonique du compte payé ;
- `teacher_id` reste temporairement pour compatibilité avec le frontend actuel et les pièces historiques en texte libre ;
- un trigger synchronise les deux champs lorsqu'ils représentent un vrai compte ;
- une incohérence entre deux comptes réels est refusée avec `PAYROLL_USER_MISMATCH` ;
- la suppression d'un compte met `user_id` à `NULL` sans supprimer la pièce comptable ni son ancien libellé `teacher_id`.

### Raccordement Claude

Pour une nouvelle fiche, écrire de préférence :

```js
{ user_id: user.id, teacher_id: user.id, ... }
```

La double écriture est transitoire. Les lectures peuvent conserver :

```js
p.user_id || p.teacher_id
```

## 4. RPC de versement

### `mark_salary_paid(p_salary_id text)`

- **Exécuteurs autorisés :** `direction`, `direction3` ;
- **anon :** aucun droit ;
- **action unique :** modifie seulement `paid`, `paid_date` et `updated` ;
- **ne modifie jamais :** `amount`, `bonus`, `rat_prime`, `deductions`, `adv_total`, `net`.

### Réponses

```json
{
  "ok": true,
  "code": "SALARY_PAID",
  "message": "Versement du salaire confirmé.",
  "data": {
    "id": "...",
    "paid": true,
    "status": "paid",
    "paid_date": "YYYY-MM-DD",
    "amount": 100,
    "net": 100
  }
}
```

Codes possibles :

```text
SALARY_PAID
SALARY_ALREADY_PAID
SALARY_NOT_FOUND
ACCESS_DENIED
```

### Raccordement Claude obligatoire

Dans `quickPayTeacher`, remplacer l'écriture directe :

```js
pushSync('salaries','patch',{paid:true,paid_date:today(),status:'paid'}, ...)
```

par :

```js
const r = await _rpc('mark_salary_paid', { p_salary_id: sal.id });
```

Puis :

1. attendre `r.ok === true` avant d'afficher le succès ;
2. mettre à jour la copie mémoire avec `r.data.paid` et `r.data.paid_date` ;
3. dériver l'étiquette visuelle `status = paid ? 'paid' : 'pending'` sans l'envoyer à la base ;
4. traduire les quatre codes ci-dessus ;
5. ne jamais retomber sur un `pushSync` direct pour le versement : ce repli redonnerait à la Caisse la possibilité de modifier la fiche.

Le versement exige une connexion. Il ne doit pas être annoncé comme effectué dans la file hors ligne.
